# Demand forecast model

Trains the model behind the admin **AI Demand Forecast** screen and exports it for on-device
inference.

## What this is, honestly

The training data is **synthetic** — generated by `synthetic.py`, not collected. A model trained on
it learns the structure that generator injects: day-of-week seasonality, per-trade weather
sensitivity, annually recurring festival spikes, and ±15% noise.

That makes the reported metrics a valid measure of **whether the pipeline fits**, and not evidence
of real-world forecasting skill. Please don't present it as the latter.

What *is* real: the coefficients are genuinely fitted rather than hand-picked, inference runs
entirely on the device, and the forecast responds to real bookings placed in the app (see
"Live data" below).

## Setup

```bash
pip install -r ml/requirements.txt
```

## Pipeline

```bash
python ml/generate_dataset.py     # -> ml/data/demand_daily.csv  (not committed; reproducible)
python ml/train.py                # -> src/data/forecastModel.json  (committed; the app reads it)
```

`train.py` prints MAE / MAPE / R² for three models on a **chronological** holdout (the last 20% of
dates, so nothing from the future leaks into training):

| model                 | role |
|-----------------------|------|
| `wma_7`               | the recency-weighted average the app used before any model existed — the baseline to beat |
| `ridge`               | linear; weaker, but its flat weight vector could be updated on-device with SGD |
| `gradient boosting`   | what the app uses |

If gradient boosting fails to beat `wma_7`, `train.py` says so plainly instead of shipping it as an
improvement.

## Verification

Three checks, because a silently-wrong model still produces plausible-looking numbers.

```bash
python ml/check_parity.py       # Python generator == demandHistory.js, day by day
python ml/check_inference.py    # mlForecast.js == the exported model, numerically
```

`train.py` additionally asserts in-process that the exported JSON reproduces the fitted estimator
before writing it, and refuses to write if it does not.

Two real bugs these caught, both worth knowing if you touch the export:

- **A leaf is `children_left == -1`**, not `feature == -1`. sklearn stores `TREE_UNDEFINED = -2` in
  `feature` at leaves, so the naive test walks off the arrays and hangs.
- **Thresholds must be exported unrounded, and compared in float32.** sklearn casts `X` to float32
  before traversal and its thresholds are float32 widened to float64. Rounding a threshold — even to
  9 decimals — moves it below its true value and misroutes any sample sitting exactly on that
  boundary. `mlForecast.js` mirrors the precision with `Math.fround`.

## Live data

The app does not retrain. It scores fresh features every run, and those features come from
`src/data/demandHistory.js`, which overlays **real bookings** from MMKV onto a deterministic
synthetic baseline. So new activity moves the forecast without any retraining.

To fold accumulated real bookings into the *weights*, export them and re-run `train.py`. Note a demo
session produces a handful of bookings — enough to shift lag features visibly, nowhere near enough
to fit a model on.

## Keeping the two generators in sync

`synthetic.py` duplicates constants from `src/data/mockHistoricalDemand.js` (categories, base
demand, day multipliers, zone weights, festivals). Change them in one place and they must change in
the other — `check_parity.py` is what catches the drift.

## Zone

`generate_dataset.py` emits `zone_*` columns so a zone-level model can be trained without
regenerating anything, but the shipped model does not use them. Bookings carry a free-text address
and no zone, so a zone prediction could not be validated against real activity. The zone heatmap in
the app remains synthetic until a zone is captured at booking time.
